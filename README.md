# Отчет студента 420 группы Иванникова Даниила по заданию "Построение системы микросервисов для поддержки дипломной работы"

## Задача

    Проектирование и реализация системы для помощи в запуске и настройке гиперпараметров для научной работы. 
    
## Требования
    
    Поддержка моделей, реализованных на разных ЯП или на разных версиях одного ЯП, загрузка и предпросмотр изображений из набора данных, интерактивное отображение прогресса обучения моделей, хранение всех предыдущих запусков и их метрик.

### В ходе задания были реализованы:
1) Система, состоящая из 5 основных модулей:
    a) Collector service - модуль, отвечающий за получение и валидацию структуры набора данных при его добавлении на сайте, структурирование файлов набора данных в объектном хранилище MinIO, а также за выдачу разметки и изображений датасета по индексам

    b) Storage service - модуль, отвечающий за работу с Базой Данных PostgreSQL, принимающий запросы от остальных четырех модулей. Ответственен за добавление, изменение и удаление записей в таблицах базы данных

    c) ML service - модуль, отвечающий за регистрацию, валидацию и взаимодействие с моделью. Состоит из двух отдельных процессов - Worker и Service. Service занимается обработкой запросов на регистрацию моделей и отправкой информации в storage-service для последующего занесения её в БД, а Worker - первоначальной валидацией моделей и их запусками

    d) Web service - модуль, занимающийся взаимодействием с пользователем, обработкой его запросов, маршрутизацией информации к верному обработчику. Представляет собой многостраничный вебсайт (стек: html + js) и Python-код с библиотекой Flask

    e) Visualization service - модуль, занимающийся построением графиков из информации после обучения модели

2) Тестовый автокодировщик для проверки работы системы, запускаемый в докере и используемый мной в научной работе (Deep Perceptual Autoencoder)

3) 2 zip архива для загрузки на сайт в качестве датасетов с файлами разметки .csv и .json соответственно (./test_data/dataset_templates/)


## Запуск и развёртывание системы

### Развёртывание:

    git clone https://github.com/DeM0nIkGames/microservices

    cd ./system-main

    docker network create ml-model-network

    docker compose build

### Запуск:

    docker compose up -d

    Затем на сайте адрес для регистрации: http://dpa-model-service:8000

## Возможности и сценарии использования системы:
1) Работа с пользователями

    В системе реализованы роли пользователей. Есть 2 роли - администратор (admin) и пользователь (user). Реализовано базовое различие прав, обычный пользователь не может взаимодействовать с системой, добавляя, удаляя или запуская модели и датасеты. Реализована авторизация и аутентификация пользователей (страница /login). Для админов добавлена работа с пользователями (на странице "/users"), возможность удалять, добавлять и изменять их. Для всех ролей пользователей реализована возможность (сверху справа) выйти из аккаунта или поменять пароль

2) Добавление моделей

    В системе реализована работа с моделями, развёрнутыми в докерах. Такое решение было принято ввиду различия версий ЯП и библиотек реализации моделей. Для удобства пользователя и избежания ошибок непосредственно при обучении/инференсе модели, реализована процедура валидации модели, включающая в себя проверку ответа модели на 4 основных запроса:
        GET "/metadata" - возвращение метаинформации о модели, её версии, версии api, гиперпараметрах для дальнейшей работы, их описания
        POST "/sessions/" - создание сессии работы с моделью, инициализация весов сети, других вспомогательных сущностей
        POST "/sessions/<id>/batch" - пересылка батча в открытую сессию модели, изображения кодируются с помощью Base64. Тестовый запрос содержит одно тестовое изображение 1х1
        POST "/sessions/<id>/close" - закрытие сессии работы с моделью
    В случае неуспешной валидации модель получит статус "failed" в левом верхнем углу страницы, и кнопка "Повторить валидацию" станет активна. В случае успешной - на странице модели появится список гиперпараметров с подсказками-описаниями и значениями по дефолту, а также с возможностью их поменять

3) Добавление наборов данных

    В системе реализовано добавление наборов данных в виде загрузки ZIP архива на сайте и их настройка. Доступны формат разметки .csv и .json; 
        Формат .csv: (relative_path,label); .json: {"label": list_of_relative_paths}
    Лимит размера архива - 10GiB. После загрузки будет доступна страница датасета, на которой будут статистики по классам изображений, изменение доли тренировочной выборки в классе, возможность поменять название класса и предпросмотр случайного изображения из каждого класса

4) Запуск моделей

    В системе реализована возможность запуска любой провалидированной модели на любом загруженном наборе данных. После выбора определенного датасета выведутся его статистики по классам в тренировочной и тестовой выборках, после чего можно будет начать запуск. На странице модели доступны все её запуски со статусами, показывающими прогресс текущего запуска. По его окончании на странице запуска (/results/<id>) появится информация по метрикам модели и её ошибкам

5) Просмотр графиков

    После успешного запуска модели на наборе данных на главной странице и на странице запущенной модели появится возможность зайти непосредственно на страницу данного запуска, где будут представлены основные метрики (Accuracy, Precision, Recall, F1, ROC AUC) на тренировочном и тестовом наборах в виде таблицы, ниже которых расположены примеры ошибок модели (ввиду возможности решения задачи многоклассовой классификации, предусмотрены ошибки вида любой пары классов X:Y, X != Y). Также, на вкладке "Графики" будут представлены графики Loss, Accuracy по эпохам, ROC и PR кривых, Confusion Matrix и отдельные Precision, Recall и F1 отдельно для каждого класса. Учитывая особенность задачи - получение итогового предсказания модели не применением функции argmax по выходам модели, а выбором threshold для anomaly_score - принято решение внедрить ползунок подбора порога, имеющего 100 позиций, на каждый перцентиль выданных значений, а также кнопка с автоматическим выбором наилучшего порога по критерию Youden

6) Версионирование моделей

    На странице провалидированной модели расположена кнопка "Зарегистрировать новую версию", по нажатию на которую можно ввести новую версию модели, после подтверждения которой будет создана отдельная страница, и начнётся валидация. Замечу, что при ответе на запрос /metadata модель должна возвращать свою версию, это сделано для удобства валидации. Она успешно завершится только при условии совпадения имени модели и её версии с возвращаемыми значениями. Разные версии модели являются независимыми экземплярами, поэтому версионность пока что базовая

7) Логгирование действий

    Collector и Storage логгируют действия в текстовые файлы. У каждого сервиса 2 файла - для всех запросов и для важных изменений в статусе (./logs/{service-name}/requests.log и audit.log соответственно).
